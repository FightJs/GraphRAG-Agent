# 向量数据库选型与创建规范 v1.0

> 适用项目：GraphRAG Agent
> 依据文档：[vector-rag-feasibility.md](./vector-rag-feasibility.md)
> 评审日期：2026-08-04
> 当前阶段：设计规范；本阶段不编写应用代码、迁移脚本或部署脚本

## 1. 目的与结论

本文规定 GraphRAG Agent 的向量存储选型、生产实例创建、数据契约、索引演进、租户隔离、备份恢复和验收要求。

**正式方案：PostgreSQL + pgvector。** 向量与用户、知识库、文档及分块元数据存放在同一个 PostgreSQL 数据库中，通过事务和统一备份保证一致性。当前开发环境可以继续使用 SQLite，但 SQLite 不属于生产向量数据库方案。

本规范只定义约束和接口边界，不改变当前实现。后续实现必须以本文为准，并通过数据库迁移引入所需对象。

## 2. 选型决策

### 2.1 决策矩阵

| 方案 | 结论 | 主要原因 |
| --- | --- | --- |
| PostgreSQL + pgvector | **采用** | 与业务数据共库，事务、备份和权限模型统一；适合当前中小规模、多租户场景 |
| Qdrant | 备用 | 适合向量规模和检索能力独立扩展，但增加服务、网络、备份和运维边界 |
| Milvus/专用向量集群 | 暂不采用 | 当前规模与运维能力不足以抵消额外复杂度 |
| SQLite 文件/内存索引 | 仅本地演示 | 不满足多实例、持久化、并发、备份和故障恢复要求 |

### 2.2 适用边界

本方案面向文本 chunk 的语义近邻检索，不承担对象存储、全文检索或知识图谱存储职责。关键词检索和图谱检索仍由各自模块提供，后续通过 hybrid/RRF 组合；不得把它们混写成向量表中的隐式字段。

当向量数据量、查询并发或延迟目标超出单 PostgreSQL 实例能力时，需重新评审 Qdrant 或专用集群，并保持本文定义的 `chunk_id`、租户过滤和索引版本语义不变。

## 3. 目标环境与版本基线

### 3.1 环境

- 生产：托管 PostgreSQL（当前部署方向为 Railway PostgreSQL）并启用 pgvector 扩展。
- 本地：Docker PostgreSQL，使用与生产相同的大版本和 pgvector 主版本；不以 SQLite 模拟向量类型或近似索引行为。
- 应用连接：沿用 SQLAlchemy 异步连接体系；数据库 URL、凭据和 SSL 参数由 Secret/环境变量注入，禁止写入仓库。

### 3.2 版本基线

- PostgreSQL：16 或更高版本；生产与预发布必须保持同一大版本。
- pgvector：0.8 或更高版本；具体补丁版本由托管服务锁定并记录在部署清单中。
- 向量距离：第一阶段统一使用 cosine distance；如改用 inner product 或 L2，必须新建索引版本并重新评测。

版本升级须先在预发布环境验证扩展加载、索引构建、查询计划、备份恢复和 Recall@K，不得直接在生产执行大版本或扩展升级。

## 4. 数据模型契约

### 4.1 逻辑对象

建立业务表 `document_chunks`，它是“一个可被召回的文本证据单元”。表名、字段语义和稳定标识如下：

| 字段 | 类型约束 | 必填 | 规则 |
| --- | --- | --- | --- |
| `chunk_id` | UUID 或现有字符串 ID，主键 | 是 | 全局稳定；作为 upsert、引用和删除的幂等键 |
| `owner_id` | 与 `users.user_id` 同类型，外键 | 是 | 服务端生成/校验，永远不能信任客户端传入值 |
| `kb_id` | 与 `knowledge_bases.kb_id` 同类型，外键 | 否 | 单文档知识库为空时允许为空；非空时必须属于 `owner_id` |
| `doc_id` | 与 `documents.doc_id` 同类型，外键 | 是 | 必须属于 `owner_id`，删除文档时级联或可靠异步删除 |
| `chunk_index` | 非负整数 | 是 | 同一文档内从 0 开始且唯一 |
| `page_start/page_end` | 非负整数，可空 | 否 | 能定位页码时填写；无法定位时为空，不伪造页码 |
| `char_start/char_end` | 非负整数，可空 | 否 | 原规范化文本中的半开区间 `[start, end)` |
| `content` | 非空文本 | 是 | 保存用于 embedding 和引用的规范化文本；不得保存密钥 |
| `content_hash` | 固定长度十六进制摘要 | 是 | 对规范化 content 计算，用于跳过重复 embedding |
| `embedding` | `vector(D)` | 是（索引完成时） | `D` 由实际模型响应确认后登记；同一索引版本不得混用维度 |
| `embedding_model` | 非空字符串 | 是（有 embedding 时） | 记录完整 provider/model 标识 |
| `index_version` | 非空字符串 | 是 | 绑定 chunk 策略、模型、维度和距离度量；变更即新版本 |
| `created_at/updated_at` | 带时区时间戳 | 是 | 由数据库或服务端统一写入 |

### 4.2 约束与索引（逻辑要求）

- `doc_id + chunk_index` 唯一。
- `owner_id`、`kb_id`、`doc_id` 分别建立普通 B-tree 索引；查询必须先应用授权过滤，再进行向量排序。
- `content_hash + embedding_model + index_version` 建立可用于幂等判断的唯一语义约束。若同一 chunk 可能跨文档复用，唯一约束范围不得错误地扩大到全表。
- 外键删除策略必须避免孤儿向量；推荐文档删除与 chunk 删除在同一事务中完成，异步补偿仅作为故障恢复手段。
- 需要保留历史索引时，旧版本数据不得参与默认查询；通过 `index_version` 显式选择并在重建完成后切换活动版本。

### 4.3 维度与模型登记

向量维度不得根据模型名称猜测或写死在业务配置中。首次接入模型时，用真实 embedding 响应确认维度，并登记：provider、model、dimension、distance、chunk policy、`index_version`、启用时间。模型、维度、归一化方式或 chunk 策略任一变化，都必须生成新的 `index_version`，禁止在同一向量列中混存不可比较向量。

## 5. 检索与索引规范

### 5.1 阶段一：精确检索优先

初次建库和上线验收使用 pgvector 精确近邻搜索，以验证权限、相似度、引用和评测基线。默认查询流程为：

1. 服务端根据当前登录用户解析授权的 `owner_id`、`kb_id` 和 `doc_id` 范围。
2. 以同一模型生成 query embedding。
3. 在活动 `index_version` 范围内按 cosine distance 排序并取候选 Top-K（初始值 10）。
4. 依据离线评测确定最低相似度阈值；阈值未校准前不得用未经验证的硬编码值。
5. 去重、按 token 预算截断，返回 chunk、文档、页码/位置和 score 作为来源。

### 5.2 阶段二：近似索引

只有当真实数据量、P95 延迟和召回目标证明精确查询不足时，才启用 HNSW；IVFFlat 作为需要更低构建成本时的备选。近似索引参数（如 HNSW 的 `m`、构建 `ef_construction`、查询 `ef_search`）必须通过基准测试确定并记录，不能只沿用示例默认值。

创建或重建大型索引使用不阻塞业务的运维流程，并单独监控构建耗时、锁等待、磁盘增长和 Recall@K。任何近似索引上线都必须与精确检索对照验证。

### 5.3 多租户隔离

`owner_id` 是每次向量检索的强制条件；前端不得决定过滤范围。`kb_id`、`doc_id` 过滤必须再经过关系表授权校验。生产可增加 PostgreSQL Row-Level Security 作为纵深防御，但不能替代应用层授权。日志、指标和错误信息不得暴露其他租户的 ID、原文或向量内容。

## 6. 创建与部署规范

数据库创建按以下顺序执行，由受控迁移/部署流程完成：

1. 创建独立生产数据库和最小权限应用角色；迁移角色与运行时角色分离。
2. 启用并验证 pgvector 扩展，记录 PostgreSQL/pgvector 版本。
3. 创建或迁移业务表及 `document_chunks` 契约；所有结构变更必须可审计、可回滚或有明确前滚方案。
4. 创建租户、关系和幂等所需的 B-tree 索引；确认外键与删除策略。
5. 导入/重建向量后再创建近似索引（若评测决定启用），并执行 `ANALYZE`/统计信息刷新。
6. 配置连接池上限、SSL、备份、恢复时间目标（RTO）和恢复点目标（RPO），并记录在部署清单。
7. 运行验收检查：扩展可用、维度一致、跨租户查询为空、删除无孤儿、备份可恢复。

生产禁止继续依赖启动时 `create_all` 作为 schema 管理机制；应用迁移、扩展升级和索引变更必须由版本化迁移流程执行。本阶段不实现该流程。

## 7. 写入、重建与生命周期

- 索引流水线按批次写入，单批失败可重试；只在全部必要 chunk 成功写入后将文档标记为 `indexed`。
- upsert 必须幂等：相同 `chunk_id`、content hash、模型和版本重复执行不会产生重复记录或重复计费。
- provider 超时、限流、部分响应和维度错误均使任务进入可见的失败/待重试状态；错误信息脱敏。
- 文档或知识库删除必须同步删除向量；重建采用“新版本写入并校验，完成后切换活动版本”的方式，避免半成品被召回。
- 保留必要的索引任务状态和 tombstone/审计信息，确保后台重试不会复活已删除文档。

## 8. 安全、备份与可观测性

数据库连接凭据、用户 embedding Key 和加密主密钥均由 Secret Manager 注入；数据库仅保存用户 Key 密文，不保存 Authorization Header。生产数据库启用传输加密、静态加密（由托管服务提供时）和网络访问控制。

备份必须覆盖业务表、chunk 元数据和 embedding；恢复演练必须验证扩展、索引和向量可查询。若备份体积或恢复时间不可接受，应评估独立备份策略，但不能只备份元数据而遗漏向量。

至少记录以下不含原文和密钥的指标：embedding 成功率、批次耗时、重试次数、写入数量、检索 P50/P95、候选数、零命中率、score 分布、索引构建耗时和数据库连接池耗尽次数。

## 9. 非目标与待确认项

本阶段不实现：应用 ORM 模型、Alembic/迁移脚本、embedding 调用、向量 upsert/search 服务、HNSW 调参、hybrid/RRF、reranker、图谱数据库迁移和生产部署自动化。

实施前必须确认：

- 生产托管 PostgreSQL 的可用版本、pgvector 版本和扩展启用权限；
- `qwen/qwen3-embedding-8b` 真实响应的向量维度、最大输入、限流和成本；
- 30-50 条真实问答评测集，以及 Recall@5、MRR、P95 延迟和可接受阈值；
- 文档格式到页码/字符区间的定位能力；
- 目标数据量、并发量、RPO/RTO 和磁盘预算。

## 10. 验收标准

规范进入实施阶段前，评审人应确认以下全部条件：

- 选型结论为 PostgreSQL + pgvector，备用方案及触发条件已记录；
- 数据契约覆盖租户、知识库、文档、chunk、模型、维度、版本和来源定位；
- 任一检索请求都能证明其授权过滤先于向量排序，跨租户结果为零；
- 精确检索基线、近似索引启用门槛和评测方法已定义；
- 创建顺序、迁移边界、备份恢复和密钥管理责任人明确；
- 删除、重建、失败重试和幂等行为不会产生孤儿或旧版本误召回；
- 所有待确认项均有负责人和完成前置条件。
